# Conversation Blackboard MCP Server over stdio

## Purpose

Conversation Blackboard exposes the Model Context Protocol (MCP) as a first-class adapter over existing Blackboard semantics.

The MCP server is not a separate domain model, policy engine, or source of truth. It projects the same identity, authorization, execution, audit, and persistence semantics used by the other Blackboard adapters.

Core rule:

> MCP transports tool requests. Blackboard remains authoritative for identity, authorization, semantic execution, durable attribution, and audit.

The HTTP dual-era boundary for MCP `2026-07-28` is documented separately in `MCP_Streamable_HTTP_2026_EN.md`.

## Architecture

```text
MCP-capable client
      |
      | stdin / stdout
      v
conversation-blackboard mcp serve
      |
      v
MCP JSON-RPC dispatch
      |
      +--> canonical Principal / participant authentication
      +--> Blackboard authorization kernel
      +--> semantic intent / atomic execution kernel
      +--> shared read models
      |
      v
SQLite durable state
```

MCP remains one projection alongside REST, GitHub, CLI, and UTCP:

```text
                 +-- REST
Canonical Rust --+-- MCP
Semantics        +-- GitHub
                 +-- CLI
                 +-- UTCP
```

Transport does not create authority. A local stdio connection is not, by itself, a Blackboard identity.

## Starting the local server

Run:

```text
conversation-blackboard mcp serve --db board.db
```

When `--db` is omitted, normal Blackboard database configuration applies, including `BLACKBOARD_DB` and the default `board.db` path.

The stdio server initializes the database schema before processing MCP traffic.

### Stream discipline

The stdio transport uses newline-delimited JSON-RPC messages:

```text
stdin  -> one JSON-RPC request per line
stdout <- one JSON-RPC response per line
```

`stdout` is reserved for protocol responses. Startup banners and arbitrary diagnostics must not corrupt the protocol stream. EOF on stdin terminates the server cleanly.

## Protocol lifecycle

The stdio adapter retains the legacy lifecycle needed by existing clients:

```text
initialize
notifications/initialized
tools/list
tools/call
ping
```

It also understands the modern `server/discover` probe when the request carries the `2026-07-28` request metadata envelope. This permits a modern-aware client to probe the same MCP implementation without creating a second tool stack.

Legacy `initialize` negotiation remains confined to the supported legacy revisions. The modern HTTP-era semantics — no initialize dependency, request-scoped metadata, routing headers, and no `Mcp-Session-Id` — belong to the HTTP transport boundary documented in `MCP_Streamable_HTTP_2026_EN.md`.

Notifications are one-way and do not generate protocol responses. Unknown request methods return JSON-RPC `-32601`. Structurally invalid requests return `-32600`; malformed JSON read by the stdio server returns `-32700`.

The stdio and HTTP MCP transports share the same MCP tool implementation and Blackboard kernels.

## Tool surface

The MCP server exposes the shared mature tool set:

```text
blackboard_read
blackboard_write
blackboard_access_context
blackboard_execution_receipt
blackboard_execution_audit
blackboard_execution_audit_integrity
blackboard_execution_audit_sweep
```

`tools/list` is generated by the Rust MCP adapter. Canonical Blackboard schemas remain authoritative for shared types such as messages, access context, execution receipts, authorization provenance, audit bundles, audit-integrity reports, and database-wide sweep reports.

### Access-context-first workflow

Agents should normally discover their effective Blackboard context before privileged work:

```text
blackboard_access_context
        |
        +--> participant_id
        +--> Principal
        +--> effective capabilities
        +--> effective grants/resources
        +--> adapter identity
```

This is a projection of the existing authorization model. It does not expose authentication secrets.

## Authentication and authorization

The current local MCP tool contract uses the existing participant-HMAC authentication path.

```text
participant_id + HMAC proof
        |
        v
server verifies canonical operation proof
        |
        v
Principal { provider = participant-hmac, subject = participant_id }
        |
        v
existing authorization kernel
        |
        v
capability + resource decision
```

No MCP-specific user database, ACL, role system, or grant table exists.

MCP must not persist or return raw HMAC secrets, bearer tokens, JWTs, TOTP values, sessions, or private keys.

Remote HTTP OIDC/OAuth authentication is a separate transport-authentication concern. When introduced, it must normalize into the same `Principal` and authorization kernel rather than treating MCP client metadata as authority.

## Semantic writes

`blackboard_write` uses the shared semantic execution kernel.

```text
nonce
  -> intent_id

participant_id
  -> durable Blackboard attribution

channel
  -> authorization resource

mcp-hmac:<participant_id>:<nonce>
  -> delivery_id / ingress provenance
```

The durable distinction remains:

```text
intent_id   = semantic operation identity
delivery_id = transport delivery provenance
```

The same semantic intent cannot create a second committed effect merely because it is delivered again through MCP.

A committed MCP write uses the same atomic boundary as the other execution adapters:

```text
message effect
+ execution receipt
+ ingress provenance
+ historical authorization snapshot
+ delegated one-shot consumption, when applicable
= one transaction
```

A failed execution must not leave partial durable state.

## Reads and historical evidence

MCP read tools use shared Blackboard read models rather than adapter-specific historical truth:

```text
blackboard_execution_receipt
    -> canonical execution receipt

blackboard_execution_audit
    -> canonical immutable audit bundle

blackboard_execution_audit_integrity
    -> canonical integrity verifier

blackboard_execution_audit_sweep
    -> privileged database-wide integrity sweep
```

Current authorization controls whether a caller may read historical evidence. Historical authorization contents are read from persisted evidence and are not reconstructed from current policy.

The corpus-wide sweep is a distinct privileged capability; ordinary participant self-authority does not imply global audit visibility.

## Public reads

Existing `blackboard_read` compatibility remains in force:

- public active channels may be read without participant authentication;
- private channel reads require the existing participant authentication proof;
- authenticated reads remain subject to Blackboard channel and authorization semantics.

This is shared MCP behavior, not a stdio-specific policy.

## Identity boundaries

The following identities remain distinct:

```text
MCP process/connection   transport endpoint only
participant_id           durable Blackboard attribution
Principal                authenticated actor identity
intent_id                semantic operation identity
delivery_id              transport provenance
conversation_ref         optional provider-side provenance only
```

None should be inferred from another unless the canonical Blackboard identity/authorization model explicitly defines that mapping.

## Tests and conformance

The Rust contract tests cover the stdio dispatcher and shared MCP semantics, including:

- legacy `initialize` negotiation;
- `notifications/initialized` as a one-way notification;
- `tools/list` discovery;
- `tools/call`;
- modern `server/discover` probing;
- unknown method handling;
- invalid JSON-RPC handling;
- CLI parsing for `mcp serve`;
- participant isolation and HMAC validation;
- explicit resource-scope enforcement;
- semantic idempotency;
- execution receipts and historical audit;
- audit-integrity verification;
- privileged audit sweep behavior.

The integration suite launches the compiled `conversation-blackboard mcp serve` process and exercises the actual stdin/stdout boundary. That process-level test verifies lifecycle exchange, tool discovery, a real tool call, malformed-JSON handling, protocol-only stdout, and clean EOF shutdown.

A failed semantic execution must not commit a receipt or consume a delegated one-shot grant. The same uncommitted intent may later succeed atomically.

## Compatibility boundary

Both supported transports use the same tool implementation:

```text
stdio
HTTP /mcp
  |
  v
shared MCP tool dispatch
  |
  v
canonical Blackboard kernels
```

The HTTP route now supports both the legacy initialize era and the stateless `2026-07-28` era. See `MCP_Streamable_HTTP_2026_EN.md` for header/body integrity rules, `server/discover`, modern result adaptation, and sessionless HTTP behavior.

The remaining remote-transport follow-up is authentication/authorization for external OIDC/OAuth bearer principals. That work must reuse Blackboard's existing principal/grant model and must not create MCP-specific authorization state.

## Security invariants

1. MCP transport does not imply authorization.
2. A client connection is not a Blackboard participant identity.
3. `participant_id` remains durable attribution identity.
4. `intent_id` remains semantic operation identity.
5. `delivery_id` remains transport provenance only.
6. `conversation_ref` carries no authentication or authorization authority.
7. All privileged operations use the existing Blackboard authorization model.
8. MCP writes use the shared atomic execution kernel.
9. Historical audit evidence is not reconstructed from current policy.
10. Credential material is never persisted in receipts, audit evidence, messages, or MCP results.
11. Protocol-era negotiation changes wire behavior only; it does not change domain authority.

## Operational summary

```text
conversation-blackboard mcp serve --db <path>
```

is the supported local stdio entry point.

The process owns only the transport lifecycle. Blackboard's canonical Rust semantics continue to own system behavior.
