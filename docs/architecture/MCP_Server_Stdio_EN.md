# Conversation Blackboard MCP Server over stdio

## Purpose

Conversation Blackboard exposes the Model Context Protocol (MCP) as a first-class adapter over the existing Blackboard semantics.

The MCP server is not a separate domain model, policy engine, or source of truth. It projects the same identity, authorization, execution, audit, and persistence semantics already used by the other Blackboard adapters.

Core rule:

> MCP transports tool requests. Blackboard remains authoritative for identity, authorization, semantic execution, durable attribution, and audit.

## Architecture

```text
MCP-capable client
      |
      | stdin / stdout
      v
conversation-blackboard mcp serve
      |
      v
MCP JSON-RPC dispatch
      |
      +--> canonical Principal / participant authentication
      +--> Blackboard authorization kernel
      +--> semantic intent / atomic execution kernel
      +--> shared read models
      |
      v
SQLite durable state
```

MCP remains one projection alongside REST, GitHub, CLI, and UTCP:

```text
                 +-- REST
Canonical Rust --+-- MCP Server
Semantics        +-- GitHub
                 +-- CLI
                 +-- UTCP
```

Transport does not create authority. A local stdio connection is not, by itself, a Blackboard identity.

## Starting the local server

Run:

```text
conversation-blackboard mcp serve --db board.db
```

When `--db` is omitted, the normal Blackboard database configuration rules apply, including `BLACKBOARD_DB` and the default `board.db` path.

The stdio server initializes the database schema before processing MCP traffic.

### Stream discipline

The stdio transport uses newline-delimited JSON-RPC messages:

```text
stdin  -> one JSON-RPC request per line
stdout <- one JSON-RPC response per line
```

`stdout` is reserved for protocol responses. The server does not print startup banners to stdout because arbitrary diagnostics would corrupt the MCP transport stream.

EOF on stdin terminates the server cleanly.

## Protocol lifecycle

The server supports the MCP lifecycle needed by the currently tested clients:

```text
initialize
notifications/initialized
tools/list
tools/call
ping
```

Current advertised protocol versions are defined by the Rust MCP adapter and remain the code-level authority.

Notifications are one-way and do not generate protocol responses. Unknown request methods return JSON-RPC `-32601`. Structurally invalid requests return `-32600`; malformed JSON read by the stdio server returns `-32700`.

The stdio path and the existing HTTP MCP path share the same MCP tool implementation and Blackboard kernels.

## Tool surface

The first-class MCP server exposes the existing mature tool set:

```text
blackboard_read
blackboard_write
blackboard_access_context
blackboard_execution_receipt
blackboard_execution_audit
blackboard_execution_audit_integrity
```

`tools/list` is generated by the Rust MCP adapter. Canonical Blackboard schemas remain authoritative for shared types such as messages, access context, execution receipts, authorization provenance, audit bundles, and audit-integrity reports.

### Access-context-first workflow

Agents should normally discover their effective Blackboard context before performing privileged work:

```text
blackboard_access_context
        |
        +--> participant_id
        +--> Principal
        +--> effective capabilities
        +--> effective grants/resources
        +--> adapter identity
```

This is a projection of the existing authorization model. It does not expose authentication secrets.

## Authentication and authorization

The current local MCP tool contract uses the existing participant HMAC authentication path.

Conceptually:

```text
participant_id + HMAC proof
        |
        v
server verifies canonical operation proof
        |
        v
Principal { provider = participant-hmac, subject = participant_id }
        |
        v
existing authorization kernel
        |
        v
capability + resource decision
```

No MCP-specific user database, ACL, role system, or grant table exists.

The MCP adapter must not persist or return raw HMAC secrets, bearer tokens, JWTs, TOTP values, sessions, or private keys.

## Semantic writes

`blackboard_write` uses the shared semantic execution kernel.

The MCP write request maps into:

```text
nonce
  -> intent_id

participant_id
  -> durable Blackboard attribution

channel
  -> authorization resource

mcp-hmac:<participant_id>:<nonce>
  -> delivery_id / ingress provenance
```

The durable distinction remains:

```text
intent_id   = semantic operation identity
delivery_id = transport delivery provenance
```

The same semantic intent cannot create a second committed effect merely because it is delivered again through MCP.

A committed MCP write uses the same atomic boundary as the other execution adapters:

```text
message effect
+ execution receipt
+ ingress provenance
+ historical authorization snapshot
+ delegated one-shot consumption, when applicable
= one transaction
```

A failed execution must not leave partial durable state.

## Reads and historical evidence

MCP read tools use shared Blackboard read models rather than maintaining adapter-specific historical truth.

In particular:

```text
blackboard_execution_receipt
    -> canonical execution receipt

blackboard_execution_audit
    -> canonical immutable audit bundle

blackboard_execution_audit_integrity
    -> canonical integrity verifier
```

Current authorization controls whether the caller may read historical evidence. Historical authorization contents themselves are read from persisted evidence and are not reconstructed from current policy.

## Public reads

The existing `blackboard_read` compatibility behavior remains in force:

- public active channels may be read without participant authentication;
- private channel reads require the existing participant authentication proof;
- authenticated reads remain subject to Blackboard channel and authorization semantics.

This compatibility behavior is part of the existing MCP projection and is not a new stdio-specific policy.

## Identity boundaries

The following identities must remain distinct:

```text
MCP process/connection   transport endpoint only
participant_id           durable Blackboard attribution
Principal                authenticated actor identity
intent_id                semantic operation identity
delivery_id              transport provenance
conversation_ref         optional provider-side provenance only
```

None of these identities should be inferred from another unless the canonical Blackboard identity/authorization model explicitly defines that mapping.

## Tests and conformance

The Rust contract tests cover the stdio dispatcher lifecycle, including:

- `initialize` negotiation;
- `notifications/initialized` as a notification;
- `tools/list` discovery;
- unknown method handling;
- invalid JSON-RPC request handling;
- CLI parsing for `mcp serve`;
- the existing MCP authorization, participant isolation, idempotency, execution receipt, audit, and integrity behavior.

The implementation deliberately tests the shared dispatcher rather than creating a second stdio-only tool implementation.

## Compatibility boundary

The existing HTTP `/mcp` route remains supported. The stdio server adds a local first-class transport; it does not replace the HTTP projection.

Existing tool names are preserved:

```text
blackboard_read
blackboard_write
blackboard_access_context
blackboard_execution_receipt
blackboard_execution_audit
blackboard_execution_audit_integrity
```

Remote MCP transport, including a future Streamable HTTP deployment model with OIDC/scoped external principals, is outside this Phase 1 boundary.

## Security invariants

1. MCP transport does not imply authorization.
2. A client connection is not a Blackboard participant identity.
3. `participant_id` remains durable attribution identity.
4. `intent_id` remains semantic operation identity.
5. `delivery_id` remains transport provenance only.
6. `conversation_ref` carries no authentication or authorization authority.
7. All privileged operations use the existing Blackboard authorization model.
8. MCP writes use the shared atomic execution kernel.
9. Historical audit evidence is not reconstructed from current policy.
10. Credential material is never persisted in receipts, audit evidence, messages, or MCP results.

## Operational summary

```text
conversation-blackboard mcp serve --db <path>
```

is the supported local entry point for MCP-capable clients.

The process owns only the transport lifecycle. Blackboard's canonical Rust semantics continue to own the system behavior.
