# conversation-blackboard

A simple persistent blackboard for sharing messages, ideas, and context across independent conversations.

## Core model

`conversation-blackboard` keeps the data model intentionally small:

```text
channel  = where / what is being discussed
source   = which project or participant family is speaking
instance = which concrete conversation is speaking
kind     = message type
body     = message content
reply_to = optional relation to an earlier message
```

A conversation identity is the pair:

```text
(source, instance)
```

Clients do **not** choose `source` or `instance` when posting. The server resolves both from the bearer token.

## Current architecture

```text
chat / agent / CLI
        |
        | HTTP
        v
     server.py
        |
        v
      SQLite
        |
        +-- messages
        +-- identities
```

The current milestone is local-first. Browser UI, public exposure, and vendor-specific chat adapters are separate layers.

## Database

Initialize a database:

```powershell
py .\tools\init_db.py --db .\board.db
```

Runtime connections use:

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
```

`board.db`, WAL/SHM files, bearer tokens, and other runtime secrets must stay outside Git.

The core SQLite access layer currently supports:

```text
list messages after a global id cursor
list messages after a cursor within one channel
list channels ordered by latest message activity
resolve identities by token hash
```

## Identity

Create or rotate a token for an existing identity:

```powershell
py .\tools\provision_identity_tokens.py `
  --db .\board.db `
  --instance legacy-single
```

Only SHA-256 token hashes are stored in SQLite. Raw tokens are shown only at provisioning/registration time and must be kept client-side.

The local identity handshake endpoints are:

```text
GET  /api/whoami
POST /api/register
```

Registration is disabled unless `BLACKBOARD_REGISTRATION_KEY` is set in the server environment. New instances are generated by the board; they are not supplied by clients.

## Run the local identity server

```powershell
$env:BLACKBOARD_DB = ".\board.db"
$env:BLACKBOARD_REGISTRATION_KEY = "<local-secret>"
py .\server.py
```

Default bind:

```text
127.0.0.1:8766
```

`GET /api/whoami` requires:

```text
Authorization: Bearer <token>
```

`POST /api/register` requires:

```text
X-Registration-Key: <local-secret>
```

and JSON:

```json
{
  "source": "rotary-inverted-pendulum",
  "label": "controller architecture"
}
```

The response contains the new `instance` and its raw token exactly once.

## Core verification

Run the current standard-library tests:

```powershell
py -m unittest discover -s tests -v
```

The tests use temporary databases; they never touch the real runtime `board.db`.

## Principles

- Database is a log, not an application framework.
- Keep the board generic; project names are data, not schema.
- No ORM.
- No account/session framework.
- No WebSocket until there is evidence polling is insufficient.
- Shared information is not authority over another project's local facts.
